# Docker deployment

This image packages and verifies **Codex only**. `SZPONT_RUNNER` must be `codex`;
Claude Code and OpenCode are [experimental host adapters](runners.md) and require
their own installation, auth storage and isolation acceptance.

The engine image contains the compiled TypeScript service, Node 24.22.2, Codex CLI
0.166.0, Git, GitHub CLI, ripgrep, `flock` and a small init process. It runs as UID/GID 1000,
publishes no ports, and includes neither a browser nor authentication. Model access
still requires your own supported Codex account and consumes that account's allowance.

The base image is pinned by its multi-platform digest. The release image is built for
Linux `amd64` and `arm64`; prefer a published release digest for a deployment you can
reproduce. Rebuilding later can pick up newer Debian security packages.

## First start

Install Docker Engine with the Compose plugin. Clone the public source and copy
`.env.example` to an absolute private file **outside** the checkout. Replace the token
and Discord IDs, then restrict the file to your account:

```sh
chmod 600 /absolute/private/szpont.env
export SZPONT_ENV_FILE=/absolute/private/szpont.env
export SZPONT_IMAGE=ghcr.io/dalkedev/szpont-engine:0.8.0
docker compose config --quiet
docker compose pull
docker compose run --rm engine init
docker compose run --rm engine sandbox-check
docker compose run --rm -it engine login
docker compose run --rm engine login-status
docker compose up -d --no-build
docker compose logs --tail=50 engine
```

Complete the device login on the official page printed by Codex. Enter credentials
only there. Stop the engine before running `login` again: initialization, login and
the engine share an exclusive state-volume lock. A competing instance exits with code
75 before opening SQLite or performing startup recovery.
The engine also runs `sandbox-check` under that lock before connecting to Discord;
an incompatible sandbox stops startup before the bot can accept a task.

`init` creates synthetic Markdown templates and a local Git repository inside the
workspace volume. It refuses to replace an existing workspace. Edit those private
templates for your own installation before asking the agent to act. The container
paths override the example's host paths; do not put Docker credentials in the image.

Compose reads bot credentials from your private environment file. Anyone with Docker
administrator access can inspect a container's environment and mounted volumes; Docker
access is privileged host access. Do not print `docker compose config` without `--quiet`
or paste `docker inspect` output into issues.

## Persistent data

| Named volume | Container path              | Contents                                                                               |
| ------------ | --------------------------- | -------------------------------------------------------------------------------------- |
| `workspace`  | `/var/lib/szpont/workspace` | Private Markdown, conversations and local Git history; active workspace is `current/`. |
| `state`      | `/var/lib/szpont/state`     | Durable SQLite queue and exclusive instance lock.                                      |
| `artifacts`  | `/var/lib/szpont/artifacts` | Results generated by agent tasks.                                                      |
| `codex-auth` | `/var/lib/szpont/codex`     | Codex authentication, private configuration and session history.                       |
| `github-auth` | `/var/lib/szpont/github`   | Separate private GitHub CLI credentials and configuration.                             |

The five volumes have separate lifecycles from the image. `docker compose down` keeps
them; **`docker compose down --volumes` deletes them**. Never point a public Git remote
at these volumes or copy them into a build context. Fresh named volumes inherit the
image's non-root ownership. If you choose bind mounts instead, create their directories
with UID/GID 1000 ownership and restrictive permissions yourself; the entrypoint does
not run as root or repair host ownership.

Back up stopped volumes together, or use SQLite's supported backup/checkpoint procedure.
Copying just the main database file while WAL is active can lose jobs. Keep auth-volume
backups private. Upgrades preserve volumes, but always back up state before changing
versions and check the release notes for migrations.

## Local build and offline acceptance

```sh
docker build -t szpont-engine:local .
sh scripts/docker-smoke.sh szpont-engine:local
export SZPONT_IMAGE=szpont-engine:local
docker compose up -d --no-build
```

The smoke runs with networking disabled, no credentials, a read-only root filesystem
and fresh disposable volumes. It checks the non-root user, runtime pins, exclusive
workspace initialization, read-only application files and SQLite data across container
restarts. It also exercises the actual Codex sandbox: workspace/artifact writes must
succeed and a write to the separate authentication volume must fail. It sends no real
messages and makes no model call. It is not proof of Discord connectivity or model access.

Compose drops Linux capabilities, enables `no-new-privileges`, limits process count and
rotates local logs. The application and image source remain read-only; only the private
volumes and temporary filesystem are writable. Keep one engine instance per state volume.

The supplied seccomp profile permits the unprivileged user and mount namespaces needed
by Codex's Bubblewrap sandbox while retaining a syscall allowlist. Docker's ordinary
default profile blocks that inner sandbox. The profile is copied unchanged from
[OpenAI codex-security](https://github.com/openai/codex-security/blob/522d19eefb28075e88744b7fbc61ccc013ac9732/docker/codex-security-seccomp.json)
and retains its [Apache-2.0 license](../scripts/docker-seccomp-LICENSE). It does not add
Linux capabilities or grant access to the host Docker socket.

`HOME` is `/tmp/szpont-home`, created privately with mode 0700 at startup. This gives
developer tools a writable temporary home and npm cache even though the application
filesystem is read-only. Those caches disappear when the container is replaced;
Codex authentication, configuration and sessions stay in the separate persistent
`CODEX_HOME` volume. The sandbox preflight also checks an actual npm-cache write.

### AppArmor hosts

Some Linux hosts, including Ubuntu configurations with restricted unprivileged user
namespaces, also need a host AppArmor profile. First run `sandbox-check`. If it fails,
ask the host administrator to review and install `scripts/docker-apparmor`, adapted
from the same upstream commit with the profile name changed. These are explicit host
administration steps; the image and smoke scripts never run them automatically:

```sh
sudo install -m 0644 scripts/docker-apparmor /etc/apparmor.d/szpont-engine-container
sudo apparmor_parser -r -W /etc/apparmor.d/szpont-engine-container
export COMPOSE_FILE=compose.yaml:compose.apparmor.yaml
docker compose run --rm engine sandbox-check
```

Then use that same `COMPOSE_FILE` for subsequent Compose commands. For an offline image
smoke on this host, export `SZPONT_DOCKER_APPARMOR_PROFILE=szpont-engine-container` before
running `scripts/docker-smoke.sh`. Do not apply this override on hosts without AppArmor.

There is no process-only Docker `HEALTHCHECK`: a living PID does not prove Discord or
Codex works. Verify the service's structured `ready` event, private owner/forum validation
and a harmless local acceptance task before enabling consequential account actions.

Codex keeps the engine's `workspace-write` sandbox and `never` approval policy. If the
host kernel/container runtime refuses that sandbox, treat it as a deployment failure.
Do not fix it with `--privileged`, host Docker socket access or disabled sandboxing.

## Optional browser

The image does not contain Camoufox, a desktop, noVNC, logged-in profiles or an MCP server.
Provision the optional [browser package](../packages/browser/README.md) independently.
Its local stdio MCP command must be executable **inside the engine's environment** and
reach a working private display/profile. A host path or host Python command alone will
not become available inside Docker. An extended private image or a separately secured
bridge is an operator integration, not something this Compose file silently exposes.

References: [Docker volume behavior](https://docs.docker.com/engine/storage/volumes/) and
[Codex security](https://developers.openai.com/codex/security/).
